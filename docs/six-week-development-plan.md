# CampusAI 六周开发计划与人员任务分工

> 编制日期：2026 年 11 月 22 日。适用项目：校园 AI 课程知识助手。团队规模：6 人。本文为开发计划，任务、指标和交付物均不代表已经完成。

本计划沿用现有开题方案中的六位成员与主责，保留学生微信小程序、教师及管理员 Web 后台、课程资料管理、课程内检索、带引用的 AI 问答和基础练习。将原八周安排压缩为六周：第一周同时完成设计与基础工程，第二周打通资料链路，第三周交付检索与练习基础，第四周完成功能集成，第五周集中测试与修复，第六周完成部署复验和答辩交付。

### 1.2 人力与实施前提

- 规划按每人每周约 **15 至 18 小时有效投入**估算，六周共约 540 至 648 人时，包含编码、联调、评审、测试和文档。该投入需团队在第一周核实，不视为成员已经承诺。
- 你担任技术负责人，负责技术决策、接口协调、范围控制与版本验收。技术负责人是团队成员兼任职责，不增加第七个开发岗位；实名任务仍按现有 A 至 F 分工列出。
- 小程序首轮以开发者工具及可用测试设备验收，不把公众平台正式审核上线作为六周交付的前置条件。AppID、成员权限、开发环境及演示网络在第一周检查。
- 模型接口使用可用的外部服务，不安排模型训练和本地大模型部署。接口凭证与可用额度在第一周落实。
- 正式测试从第一周开始积累，第五周集中执行；需求和设计文档随模块更新，第六周负责整理核对。

## 二 六周版本的功能范围

### 2.1 必须完成的功能

| 领域 | 六周内的交付范围 | 控制实现规模的方式 |
| --- | --- | --- |
| 账号与权限 | 学生注册及登录、个人信息；教师及管理员登录；按角色和课程授权 | 不做短信、邮件验证、第三方账号绑定和复杂审批；教师及管理员由管理员维护 |
| 课程与章节 | 创建及维护课程和章节；学生加入课程；教师仅维护负责课程 | 第一周确定简单的加入方式，例如课程码；不接学校教务系统 |
| 资料管理 | 上传文本型 PDF、DOCX、TXT，查看解析状态，发布及下架，失败后重新处理 | 暂不支持扫描件 OCR、图片理解、视频、复杂 PPT 解析和批量导入 |
| 学生资料浏览 | 课程内资料列表、资料详情、收藏及取消收藏 | 使用简单列表和详情页，不做复杂文件阅读器 |
| 智能检索 | 在已加入课程的已发布资料中，用关键词及 BM25 检索原文片段 | 先把中文分词、切分、课程过滤和来源定位做正确，不引入向量数据库 |
| 引用定位 | 展示资料名、原文、页码或章节与段落位置；可查看对应来源内容 | PDF 展示页码并支持打开文件核对；DOCX、TXT 展示段落原文与定位信息；不要求任意格式精确跳转 |
| AI 问答 | 基于检索证据生成回答；保留引用；无依据提示；模型故障回退原文 | 仅单轮提问，不做多轮上下文、联网搜索或自主工具调用 |
| 问答记录与反馈 | 当前用户的历史问答、详情、简单有用或无用反馈；教师查看课程反馈 | 不做完整客服工单、复杂标签与反馈审批 |
| 练习与记录 | 手工维护单选题和判断题；提交答案、服务端判分、学习记录和错题列表 | 用按课程或章节组织的固定练习；不做自动出题、主观题批改和自适应推荐 |
| 后台管理 | 用户及角色基础管理、课程章节、资料状态、题库、问答反馈与基础统计 | 常规表单与列表；不做细粒度菜单权限配置平台 |
| 学习统计 | 课程访问量、热门问题、客观题作答正确率 | 三项汇总即可，最多配少量基础图表，不扩展成数据分析平台 |

### 2.2 暂不纳入的扩展

向量检索、混合检索、重排序模型、OCR、自动出题、多轮对话、复杂推荐、消息推送、多租户、分布式架构与自建模型均不纳入六周承诺。只有在核心验收、测试报告、部署与答辩材料全部完成后，才讨论后续版本。

发生延期时，首先简化页面装饰、统计图表数量、筛选项和非必要交互。**不以取消权限校验、引用核对、故障回退、测试与部署复验来压缩时间。**若核心练习或其他必做范围仍需调整，由技术负责人登记变更并核对课程要求，不能静默删减。

### 2.3 技术实现基线

现有开题方案拟采用 Spring Boot 3、MySQL 8，以及 Vue 3 与 Element Plus 管理后台。学生端在微信原生小程序与 uni-app 中选一种；文件存储在本地目录与 MinIO 中选一种。这些仍属于规划选型，**第一周第 2 个开发日结束前由技术负责人统一确认版本与方案**。

检索按中文分词与 BM25 实施。E 的检索模块优先采用团队能维护、能与业务后端稳定集成的方式；如果需要独立服务，第一周就明确调用协议和部署步骤，避免第三周再拆分架构。不为本项目额外引入消息中间件或复杂运维平台。

### 3.2 协作边界

- F 负责数据库结构的一致性和迁移检查，A、B、E 为自己模块编写迁移草稿及数据访问代码，不能把全部数据开发压给 F。
- 每位开发者负责自己模块的基本测试及缺陷修复，F 负责跨模块验收、复测和报告，不能由 F 一人承担全项目测试。
- E 提供可复现的解析、检索及问答接口；B 管资料业务状态，A 管权限和请求编排。三人共同验证“哪些资料能被检索”。
- C 与 D 各自主责一个端，优先复用请求封装、字段样例和设计约定。双方互审交互与接口接入，不能因前端尚未连接真实接口就把任务标记完成。
- 代码评审以 A 与 B、C 与 D 互审为主；E 的跨模块改动由 A 检查，数据库迁移由 F 与模块负责人共同检查。技术负责人只集中处理跨模块设计与高风险合并。

只要请求和响应样例确定，前端就可以开发；真实接口到位后必须替换模拟数据并验收。接口延期必须当天通知使用者，不能等周末才暴露。

### 6.2 三项必须统一的行为

1. **资料状态与发布。** 区分上传、处理中、可用和失败等处理状态，以及发布或下架状态；只有解析与索引就绪且已发布的资料可供学生检索。重试需清理半成品并避免重复入库。下架、删除和更新后，查询端立即按权威业务状态过滤旧片段，不能仅等待重建索引。
2. **问答状态与引用。** 至少区分正常生成、仅返回检索原文、资料无有效依据、请求错误。仅在有证据但模型失败时回退原文；没有有效证据时提示未覆盖。模型只能引用本次授权候选片段；来源无效时应校验失败并回退。设置请求超时，不能让页面无限等待。
3. **统计口径。** 课程访问按定义好的课程进入事件计数；热门问题按同一课程内规范化后的相同问题文本汇总，不做语义聚类；练习正确率按已提交客观题的正确题数除以总作答题数，未作答展示无数据。B 与 F 在第 3 周固定去重、时间范围及失败请求是否计入，D 按相同口径展示。

所有历史、引用、文件、题目及统计接口均需要服务端授权。前端传入的课程 ID 和隐藏的按钮都不能代替权限校验。

## 七 验收数据与测试要求

### 7.1 演示及评估数据

- 至少准备 **2 门课程，每门至少 3 份有效资料**，总资料覆盖文本型 PDF、DOCX、TXT 三种格式；另准备解析失败文件。资料使用自编或已获得使用权限的内容，并保留来源说明。
- 至少准备两名课程权限不同的学生、两名分别负责不同课程的教师以及一名管理员，用于交叉授权测试。
- 每门课程至少准备 10 道客观题，覆盖单选与判断；预置可核对的作答、错题、问答反馈及统计数据。演示账号与真实个人信息分开。
- 检索评估计划使用 **40 个问题：30 个有标注支持片段，10 个无依据问题**。划分为 20 个调参问题和 20 个最终验收问题，两部分各含 15 个有依据问题、5 个无依据问题。
- 验收集在第三周固定，由 F 保留。E 主要用调参集改进；最终评估首次结果保留。若针对验收集调参，报告必须说明，并补充新的未见问题复核，避免把调参结果当独立评估。

### 7.2 建议验收目标

下列是计划目标，第一周组内核对后执行，不是已经测得的结果。

| 验收项 | 方法 | 计划通过条件 | 主责 |
| --- | --- | --- | --- |
| 检索 Hit@3 | 在有依据的最终验收问题中，检查前三条是否包含人工标注的支持片段 | 15 个问题中至少 12 个命中，即不低于 80%；附逐题结果 | E 执行，F 复核 |
| 来源可核对 | 对返回来源与原文、页码或段落逐项核对 | 验收用例中没有不存在的资料、错误课程或伪造引用编号 | E、C、F |
| 无依据处理 | 用独立的 5 个无依据验收问题及确定无匹配片段的样例检查 | 指定样例均不展示伪造来源；记录误召回与误答，不能将其描述为对所有问题的保证 | E、A、F |
| 模型故障 | 注入超时、服务错误和无效引用，不依赖偶然外部故障 | 有证据时保留原文和来源；页面明确故障回退；无无限等待 | A、E、C、F |
| 角色与课程权限 | 对资料、文件、片段、历史、练习和后台接口直接请求 | 指定跨用户、跨课程及学生管理操作均被拒绝 | A、B、F |
| 资料生命周期 | 上传失败、重试、发布、下架、删除、更新及重建 | 不出现重复可用片段、未发布泄露或下架后仍可读旧资料 | B、E、F |
| 练习与统计 | 用固定数据手工计算，重复提交后复查 | 成绩、错题及统计与规则一致，不因重复请求重复计数 | B、D、F |
| 安装与恢复 | 非主要开发者按说明安装并恢复备份 | 能完成初始化及主流程；文件、数据库与索引对应 | A、F及交叉验证成员 |

检索与模型耗时需记录测试环境、资料规模和调用配置，再据实写报告；不预先宣称已经达到性能指标。BM25 排序分数本身不等于答案可信概率，不能直接当作已校准的置信度展示。

### 7.3 最低系统用例覆盖

F 维护不少于 30 条明确的系统验收用例，至少覆盖以下场景；模块负责人可补充自动化检查，不能用同一场景反复换输入凑数量。

| 类别 | 必须覆盖的场景 |
| --- | --- |
| 账号 | 注册、登录成功、错误密码、登录过期、禁用账号 |
| 课程权限 | 加入课程、未加入课程访问、教师管理非负责课程、学生调用管理接口 |
| 资料 | 三类有效资料、损坏文件、解析重试、未发布、下架、删除及更新后的可见性 |
| 检索来源 | 正常命中、空结果、错误课程过滤、PDF 页码、DOCX 或 TXT 段落、来源文件直接访问 |
| 问答 | 正常带引用、无依据、模型超时、外部错误、无效引用、历史与反馈归属 |
| 练习 | 两种题型、判分、空提交、重复提交、错题与学习记录、取题不泄露答案 |
| 后台与统计 | 用户角色、题库变更、反馈查询、空统计、固定数据复算 |
| 交付 | 干净安装、数据库迁移、文件备份恢复、索引重建、模型断网演示 |

缺陷等级统一为：P0 为数据泄露、越权或严重数据破坏；P1 为主要流程无法完成或结果明显错误；P2 为非阻断功能或体验问题。P0 立即处理，P1 优先修复；第五周候选版和第六周正式版均要求未解决 P0、P1 为零。

## 九 协作节奏与延期处理

### 9.1 每周固定节奏

- 周初用 20 分钟确认本周任务及依赖，单个任务尽量拆成 1 至 2 天能交付的小项。
- 开发日每人简报已完成、下一步、阻塞和需交接内容；可以异步更新任务板，不要求长会。
- 周中安排一次真实接口联调；周末安排约 30 至 45 分钟按里程碑现场操作验收。
- 合并请求尽量在一个开发日内得到回应。技术负责人每日安排固定处理时段，避免所有人等同一次集中合并。
- 每个模块的“完成”均指代码已合并、真实接口已接入、正常与关键异常已检查、文档已更新。模拟页面和本地截图不能单独作为完成证据。

### 9.2 阻塞与风险处置

| 触发条件 | 当天采取的动作 | 主责 |
| --- | --- | --- |
| 接口比约定晚一个开发日或字段冲突 | 提供固定样例供下游继续；安排最小真实接口优先交付；记录受影响任务 | 技术负责人、接口提供者 |
| 第二周资料入库尚未打通 | 暂停界面美化与 AI 扩展，A、B、E 集中修复状态、来源和索引交接 | A、B、E |
| 第三周检索效果不足 | 检查文本质量、中文分词、切分与课程过滤，使用调参集逐题定位；不临时换整套架构 | E，F 协助 |
| 第四周 B 或 C 任务积压 | 使用合并列表和简单表单完成规定功能；A 承接公共接口支持，D 协助前端联调及说明整理 | 技术负责人、A、B、C、D |
| 模型接口不可用或成本受限 | 保留真实 BM25 检索和原文引用，启用明确的回退状态；恢复模型配置，不伪装生成成功 | E、A、C |
| 第五周仍有 P0 或 P1 | 按影响逐项分配给模块负责人，当日复现、修复后复测；停止所有装饰与扩展 | 技术负责人、各模块负责人、F |
| 部署依赖成员个人电脑或小程序账号未落实 | 第 1 周落实账号，第 2 周起共享部署；第 5 周完成目标环境安装，第 6 周交叉复验 | C、F、A |
| 成员每周投入不足或临时缺席 | 当天重排任务，优先移交接口、源码、配置与剩余清单；若影响必做范围，登记变更并核对课程要求 | 项目统筹、技术负责人 |

### 9.3 技术负责人每周检查事项

- 第 1 周：确认每个人能运行、接口口径统一、数据关系成立，移除不必要的技术选型。
- 第 2 周：亲自操作一次上传到学生查看的流程，检查资料权限和来源数据。
- 第 3 周：检查真实检索与练习交付，确认问答和统计接口不会拖住两端。
- 第 4 周：组织完整业务及异常演示，冻结功能，登记全部遗留问题。
- 第 5 周：以测试和复测证据决定候选版，检查严重缺陷与文档缺项。
- 第 6 周：通过交叉部署和答辩演练决定正式交付，不以“开发者自己能运行”替代验收。

## 十 规划依据与版本维护

本计划依据现有《校园 AI 课程知识助手 项目开题汇报方案》及 2026 年 11 月 19 日的项目规划材料编制。人员映射为 A 思佳怡、B 陈用礼、C 张涵、D 卢冰玲、E 杨宇轩、F 洪少敏。当前 README 是初始化概览，本计划补充其中尚未展开的两端范围、具体业务与六周任务。

相对原八周规划，本版将需求设计与基础工程合并推进，提前进行真实接口联调和测试环境部署，缩小练习及统计的实现形式，保留最后两周用于质量和交付。第一周确定的技术栈、实际启动日期、人员可投入时间及任何范围变化，都应更新到本文件并附变更日期。技术负责人维护执行版本，周验收记录关联相应代码版本与任务。
